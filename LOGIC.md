# Spendwise — как устроена логика

Документ описывает, что делает приложение и как это реализовано: модель данных, авторизация,
автокатегоризация, месячная сводка, фронтенд и тесты.

---

## 0. Как войти (локально)

| Что | Адрес | Логин / пароль |
|---|---|---|
| **Приложение** | http://localhost:4200 | `demo@spendwise.dev` / `demo12345` (или зарегистрируй свой аккаунт кнопкой *Register*) |
| REST API | http://localhost:8080/api | Bearer-токен из `POST /api/auth/login` |
| Консоль базы H2 | http://localhost:8080/h2-console | JDBC URL `jdbc:h2:file:./data/spendwise`, пользователь `sa`, пароль пустой |

Сначала запускается бэкенд (`SpendwiseApplication` в IntelliJ), потом фронт (`npm start` в папке `frontend`).
Демо-аккаунт создаётся автоматически при первом старте. Это учебные данные только для локального запуска.

## 1. Идея

Spendwise — трекер личных финансов. Пользователь записывает доходы и расходы, а приложение:

- **само подбирает категорию** по описанию транзакции («Uber to airport» → *Transport*);
- считает **сводку за месяц**: доход, расход, баланс и разбивку расходов по категориям.

Каждый пользователь видит **только свои** данные.

## 2. Архитектура

```
 Angular 22 (localhost:4200)                     Spring Boot 4.2 (localhost:8080)
 ┌──────────────────────────┐   /api/* (proxy)   ┌───────────────────────────────────────┐
 │ pages: login, dashboard, │ ─────────────────▶ │ Security filter chain                 │
 │        categories        │  Authorization:    │   └ BearerTokenAuthenticationFilter   │
 │ core:  AuthService       │  Bearer <JWT>      │       (проверка подписи и срока JWT)  │
 │        authInterceptor   │                    │ Controllers → Services → Repositories │
 │        guards, ApiService│ ◀───────────────── │                    │                  │
 └──────────────────────────┘     JSON           │                 H2 (file)             │
                                                 └───────────────────────────────────────┘
```

Бэкенд разбит на пакеты по предметной области, а не по слоям:

| Пакет          | Ответственность                                                       |
|----------------|-----------------------------------------------------------------------|
| `auth`         | регистрация, логин, выпуск JWT, получение id текущего пользователя    |
| `user`         | сущность пользователя и репозиторий                                   |
| `category`     | категории, CRUD, алгоритм подбора категории (`CategorySuggester`)      |
| `transaction`  | транзакции, CRUD, месячная сводка                                     |
| `config`       | безопасность (JWT, CORS), настройки, демо-данные                      |
| `common`       | исключения и единый формат ошибок (`ProblemDetail`, RFC 9457)         |

## 3. Модель данных

```
users                      categories                       transactions
─────────────              ──────────────────────           ───────────────────────────
id (PK)                    id (PK)                          id (PK)
email (unique)             user_id (FK → users)             user_id (FK → users)
password_hash (bcrypt)     name   (unique в рамках user)    category_id (FK, nullable)
display_name               color  (#rrggbb)                 amount  DECIMAL(14,2)
created_at                 keywords ("uber, bolt, taxi")    type    INCOME | EXPENSE
                                                            description
                                                            date    (индекс user_id+date)
```

- Деньги хранятся в `BigDecimal`, а не в `double`, чтобы не было ошибок округления.
- У транзакции может не быть категории (`category_id = null`) — тогда в UI она «Uncategorized».
- При регистрации пользователь сразу получает 6 стандартных категорий с ключевыми словами
  (Groceries, Cafe & Restaurants, Transport, Subscriptions, Health, Salary).

## 4. Авторизация через Bearer-токен (JWT)

### Поток

```
1. POST /api/auth/login {email, password}
2. AuthService: ищет пользователя по email (без учёта регистра),
   сверяет пароль через PasswordEncoder (bcrypt)
     ├─ не совпало → BadCredentialsException → 401 "Invalid email or password"
     └─ совпало    → TokenService.issue(user)
3. Ответ: { accessToken, tokenType: "Bearer", expiresAt, user }
4. Фронт сохраняет токен в localStorage, интерсептор шлёт его в каждом запросе:
       Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
5. Spring Security (oauth2ResourceServer.jwt) на каждый запрос:
     ├─ проверяет подпись HMAC-SHA256 секретным ключом
     ├─ проверяет срок (exp)
     └─ кладёт Jwt в SecurityContext → контроллер получает его через @AuthenticationPrincipal
6. Id пользователя = claim "sub" токена (CurrentUser.id(jwt))
```

### Содержимое токена

| Claim   | Значение                    |
|---------|-----------------------------|
| `sub`   | id пользователя             |
| `email` | email                       |
| `name`  | отображаемое имя            |
| `iss`   | `spendwise`                 |
| `iat` / `exp` | время выпуска / истечения (по умолчанию 8 часов) |

### Почему так

- **Stateless**: сервер не хранит сессии, всё нужное лежит в подписанном токене. Сессии и cookies
  отключены (`SessionCreationPolicy.STATELESS`), поэтому CSRF-защита не нужна и выключена.
- Вместо самописного JWT-фильтра используются стандартные компоненты Spring Security
  (`NimbusJwtEncoder`/`NimbusJwtDecoder`, `BearerTokenAuthenticationFilter`) — меньше кода и меньше дыр.
- Секрет задаётся в `application.yml` и переопределяется переменной окружения `APP_JWT_SECRET`.

### Какие URL открыты

| Путь                 | Доступ                         |
|----------------------|--------------------------------|
| `/api/auth/**`       | без токена (логин, регистрация)|
| `/h2-console/**`     | без токена (только для разработки) |
| всё остальное        | только с валидным Bearer-токеном, иначе **401** |

## 5. Изоляция данных пользователей

Каждый запрос в репозиторий фильтруется по `ownerId`, который берётся **из токена**, а не из запроса:

```java
transactions.findByIdAndOwnerId(id, userId)   // чужая транзакция → Optional.empty()
categories.findByIdAndOwnerId(id, userId)
```

Поэтому если пользователь B попробует изменить или удалить транзакцию пользователя A по её id,
он получит **404 Not Found**. Не 403: так даже не раскрывается, что такой объект существует.
Привязать к своей транзакции чужую категорию тоже нельзя — тоже 404.

## 6. Автокатегоризация (`CategorySuggester`)

Срабатывает, когда транзакция создаётся или редактируется **без** `categoryId`.

**Алгоритм:**

1. Описание приводится к нижнему регистру.
2. У каждой категории пользователя берутся ключевые слова (строка `"uber, bolt, taxi"`
   разбивается по запятым, обрезаются пробелы, приводится к нижнему регистру).
3. Для каждой категории считается, **сколько её ключевых слов содержится** в описании.
4. Категории без совпадений отбрасываются.
5. Побеждает категория с наибольшим числом совпадений; при равенстве — та, у которой
   **самое длинное совпавшее слово** (более конкретное: «coffee beans» сильнее, чем «coffee»).
6. Если совпадений нет, категория остаётся пустой (Uncategorized).

**Пример:** «Uber eats coffee» при категориях Transport (`uber`) и Cafe (`coffee`):
по 1 совпадению, длина `coffee` = 6 > `uber` = 4 → **Cafe**.

**Явно выбранная категория всегда важнее** ключевых слов.

Тот же алгоритм доступен отдельно: `GET /api/categories/suggest?description=...`. Фронт вызывает
его, пока пользователь печатает (с задержкой 300 мс), и показывает подсказку
«✨ Will be categorized as Transport».

> Это осознанно простая эвристика. Её легко заменить на LLM или ML-классификатор:
> интерфейс `suggest(description, categories) → Optional<Category>` останется тем же.

## 7. Месячная сводка (`TransactionService.summary`)

`GET /api/transactions/summary?month=2026-11` (без параметра — текущий месяц)

1. Выбираются транзакции пользователя с первого по последний день месяца
   (`YearMonth.atDay(1)` … `atEndOfMonth()`, високосные годы учитываются).
2. `income` = сумма INCOME, `expenses` = сумма EXPENSE, `balance` = income − expenses.
3. Расходы группируются по категории; транзакции без категории попадают в группу
   «Uncategorized» (серый цвет).
4. Группы сортируются по сумме по убыванию — фронт рисует из них горизонтальные бары.

Доходы в разбивку по категориям не попадают — это разбивка именно расходов.

---

## 8. Удаление категории

При удалении категории транзакции **не удаляются**: сначала у них обнуляется `category_id`
(`TransactionRepository.clearCategory`), потом удаляется сама категория. Всё в одной транзакции БД.

## 9. Ошибки и валидация

Все ошибки возвращаются в едином формате `ProblemDetail` (RFC 9457):

```json
{ "status": 400, "detail": "Validation failed",
  "errors": { "amount": "must be greater than or equal to 0.01", "email": "must be a well-formed email address" } }
```

| Ситуация                                   | HTTP |
|--------------------------------------------|------|
| нет токена, токен поддельный или просрочен | 401  |
| неверный логин или пароль                  | 401  |
| ошибка валидации (`@Valid` на DTO)         | 400 + `errors` по полям |
| объект не найден или принадлежит другому   | 404  |
| email уже занят, категория с таким именем уже есть | 409  |

Правила валидации: email корректный, пароль ≥ 8 символов, сумма ≥ 0.01 и не больше 2 знаков
после запятой, описание до 200 символов, цвет в формате `#rrggbb`.

## 10. Фронтенд (Angular 22)

- **Standalone-компоненты, signals, zoneless** — современный Angular без NgModule и zone.js.
- **`AuthService`** хранит сессию в signal и дублирует её в `localStorage`, чтобы она пережила
  перезагрузку страницы. `isAuthenticated()` проверяет и наличие токена, и `expiresAt`.
- **`authInterceptor`**:
  - добавляет `Authorization: Bearer …` ко всем запросам, кроме `/api/auth/*`;
  - на ответ **401** (токен истёк или стал невалидным) делает logout и редирект на `/login`;
    на 401 от самого логина (неверный пароль) — нет.
- **Guards**: `authGuard` не пускает гостя на приватные страницы, `guestGuard` не пускает
  залогиненного пользователя на `/login`.
- **Ленивые маршруты** (`loadComponent`): у каждой страницы свой чанк.
- **Dashboard**: смена месяца → `effect` перезагружает сводку и список (`forkJoin`); подсказка
  категории — `valueChanges → debounceTime(300) → switchMap(suggest)`.
- В dev-режиме `/api` проксируется на `:8080` (`proxy.conf.json`), поэтому CORS при разработке
  не мешает. Для других развёртываний CORS настроен на бэкенде.

## 12. Тесты

Три уровня тестов:

| Уровень | Команда | Что это |
|---|---|---|
| **Unit** | `./mvnw test` | один класс, зависимости подменены (Mockito), без Spring и без БД. Миллисекунды |
| **API** | `./mvnw test` | весь Spring-контекст + H2 в памяти, запросы через MockMvc (без настоящего сетевого порта) |
| **Интеграционные** | `./mvnw verify` | приложение **запускается целиком на случайном порту** (настоящий Tomcat), тест ходит в него обычным HTTP-клиентом — как браузер |

`./mvnw verify` запускает все три уровня: сначала unit и API (Surefire), потом интеграционные (Failsafe, классы `*IT`).
Фронт: `cd frontend && npx ng test --watch=false`.

В IntelliJ: правый клик по `src/test/java` → *Run 'All Tests'*, или вкладка **Maven → Lifecycle → verify**.

### Unit-тесты

| Класс | Что проверяет |
|---|---|
| `CategorySuggesterTest` | совпадение без учёта регистра, приоритет более длинного слова, пустой результат |
| `TokenServiceTest` | claims в токене (`sub`, `email`, `name`, `iss`), срок жизни; токен с чужой подписью и просроченный токен отклоняются |
| `TransactionServiceTest` | расчёт income/expenses/balance, группировка и сортировка по категориям, Uncategorized, пустой месяц, границы месяца (29 февраля), автокатегория, приоритет явной категории, 404 на чужие объекты |

### API-тесты (MockMvc + H2)

| Класс | Что проверяет |
|---|---|
| `AuthApiTest` | регистрация (нормализация email, trim имени), 6 стандартных категорий, 409 на дубликат, 400 с ошибками по полям, логин → рабочий токен, 401 на неверный пароль / мусорный / подделанный токен |
| `TransactionApiTest` | полный CRUD, фильтр по месяцу и сортировка, **изоляция пользователей**, валидация |
| `CategoryApiTest` | своя категория участвует в автоподборе, 409 на дубликат имени, валидация цвета, удаление категории оставляет транзакции, `/suggest` → 200 или 204, нельзя трогать чужие категории |
| `EndToEndApiTest` | сквозной сценарий: регистрация → транзакция с автокатегорией → сводка |

### Интеграционные тесты (настоящий сервер, пакет `it`)

| Класс | Что проверяет |
|---|---|
| `DemoAccountIT` | **демо-логин из документации работает** (`demo@spendwise.dev` / `demo12345`), у демо-аккаунта есть данные за текущий месяц и 6 категорий, неверный пароль → 401 |
| `ExpenseFlowIT` | полный путь пользователя по HTTP: регистрация → своя категория → транзакции с автокатегорией → ручное исправление → сводка с точными суммами → удаление; изоляция двух пользователей |
| `InfrastructureIT` | 401 и заголовок `WWW-Authenticate: Bearer` без токена, поддельная подпись → 401; **CORS** пускает только `http://localhost:4200`; ошибки приходят как `application/problem+json`; H2-консоль открывается без токена |

Почему нужны все три уровня: unit-тесты быстрые и точно указывают на сломанный класс. API-тесты проверяют
контроллеры, валидацию и безопасность вместе. Интеграционные ловят то, чего MockMvc не видит: настройки
Tomcat, CORS-заголовки, реальную сериализацию, порядок фильтров и то, что приложение вообще стартует.

### Фронтенд (Vitest через `ng test`)

| Файл | Что проверяет |
|---|---|
| `auth.service.spec.ts` | логин и регистрация сохраняют токен, восстановление из localStorage, просроченный и битый токен = не залогинен, logout очищает сессию и ведёт на `/login` |
| `auth.interceptor.spec.ts` | добавляет Bearer, не добавляет к `/api/auth/*` и без токена, logout на 401, но не на 401 логина и не на 500 |
| `auth.guard.spec.ts` | `authGuard` и `guestGuard` пускают или редиректят |
| `api.service.spec.ts` | параметр `month`, `suggest` → категория на 200 и `null` на 204 |
| `errors.spec.ts` | понятные сообщения: бэкенд недоступен, `detail`, ошибки по полям |
